Bottle VM For-Loop Iterator Bug Fix
====================================

Problem:
--------
When two for-loops use the same iterator variable name (e.g., two "for x in spectrum" loops),
the second loop would use the iterator value left over from the first loop (17) instead of
starting from 0. This caused LED coordinates to be out of bounds (x=17 when valid range is 0-16),
resulting in a black screen.

Root Cause:
-----------
1. First loop: add_scalar() creates scalar[2] for iterator 'x'
2. Second loop: add_scalar() creates scalar[5] for iterator 'x' (duplicate)
3. Loop initialization sets scalar[5] = 0
4. But loop body references 'x' resolve to scalar[2] (via find_scalar())
5. scalar[2] still contains value 17 from first loop
6. LED operations use x=17 (out of bounds)

Solution:
---------
Modified for_statement() in bottle_compiler.cpp to reuse existing scalar if iterator
name already exists, instead of always creating a new scalar.

Code change (line ~1137):
  // Before:
  uint8_t iter_idx = add_scalar(c, &iter_token);

  // After:
  int8_t existing_idx = find_scalar(c, &iter_token);
  uint8_t iter_idx;
  if (existing_idx >= 0) {
    iter_idx = (uint8_t)existing_idx;  // Reuse existing scalar
  } else {
    iter_idx = add_scalar(c, &iter_token);  // Create new scalar
  }

Result:
-------
Both "for x in spectrum" loops now correctly use scalar[2], and the second loop
properly initializes it to 0 before starting. LED coordinates are now correct (0-16).

Test output:

  [COMPILER] for_statement: reusing scalar[2] for iterator 'x'
  [VM] OP_SET_LED #0: x_val(type=1,int=0) y_val(type=1,int=0) ✓
  [VM] OP_SET_LED #1: x_val(type=1,int=1) y_val(type=1,int=0) ✓
